# SAB Modul - план развития до глобального шрифта

Статус: проект плана, 14.11.2026. Ветка `plan/global-scripts`. План ещё не утверждён владельцем; вопросы к нему собраны в разделе 14.

## Summary (English)

SAB Modul today is a Latin and Cyrillic corporate family (Sans, Mono, Code) under SIL OFL 1.1 with the Reserved Font Name "SAB Modul".
This plan extends it region by region into a global family: Arabic script first (Arabic, Persian, Dari, Pashto, Urdu), Latin America and Southeast Asia (Vietnamese, Thai, Lao, Khmer, Burmese), China (Simplified, Traditional, Hong Kong), then the Caucasus, Greek, Hebrew, India, Japanese and Korean.
Every script ships as separate font files and WOFF2 subsets with a byte budget derived from measured open reference fonts, so that interfaces stay usable on weak mobile networks.
Every stage passes the same measurable gates: Font Bakery, OTS, Font Validator, Hyperglot and Shaperglot, HarfBuzz shaping tests, screenshots in Chromium, Firefox and WebKit, right-to-left interface checks, a reproducible build and a native-reader review.
Work is done by AI agents (design, mechanics and acceptance are separate roles); a gate is judged by a re-run measurement, never by an agent's report.
Until a script is accepted, interfaces use a paired open font (Noto or similar) through `unicode-range`; a script without native-reader review is not advertised as supported.
CJK is a separate decision between an own design and a harmonised build on an OFL base; the plan gives measured weights and work volumes for both.

## Как читать план

- 🟢 - факт проверен замером (команда или способ рядом). 🟡 - внешний факт или оценка, не сверены; до старта этапа сверяются с первоисточником (раздел 15).
- Пороги ворот названы предложением. Каждый порог фиксируется до начала рисования этапа и после этого не меняется ради зелёного отчёта (правило из `font-creation-prompt.md`).
- «Принято» значит: ворота этапа пройдены повторным замером приёмщика на чистой копии.
- Эталоны - открытые шрифты под OFL 1.1 из `github.com/google/fonts` (каталог `ofl/`) и образцы текста из `github.com/googlefonts/lang` (Apache-2.0). Они служат для замеров и сравнения; в SAB Modul не включаются (раздел 8).

```sh
          sorted({r.ScriptTag for t in ('GSUB', 'GPOS') for r in f[t].table.ScriptList.ScriptRecord}))
E
```

## 2. Целевая картина

### 2.1. Что значит «глобальный»

В Unicode около 170 письменностей 🟡. Ни один шрифт одной команды не закрывает их все; семейство Noto делалось более десяти лет большим числом студий 🟡. Поэтому цель делится на два слоя:

- **Интерфейс читается на любом языке сразу** - связкой SAB Modul и парных открытых шрифтов (раздел 10). Это результат этапа 0.
- **Свой рисунок приходит по регионам** в порядке банковских рынков и заменяет пару после приёмки.

Обязательные регионы по решению владельца: арабица с пушту; Латинская Америка; Юго-Восточная Азия; Китай; далее очередь - Япония, Корея, Индия и остальные.

Доводы порядка:

- Этап 0 идёт первым: без раннера ворот остальное принимать нечем; Латинская Америка и латиница Юго-Восточной Азии закрываются тем же рисунком за малую добавку знаков.
- Арабица - прямое требование интерфейса (арабский, пушту) и самый сложный шейпинг из ближайших; обвязка письма справа налево потом служит ивриту.
- Вьетнамский - латиница, но с двумя ярусами знаков: отдельный этап из-за высоты строки и функции `mkmk`.
- Тайская и лаосская письменности родственны и рисуются парой; кхмерская и бирманская сложнее по шейпингу (подписные согласные, перестановки).
- Китай обязателен, но решается сначала гармонизированной парой: свой рисунок - отдельное решение (раздел 9).
- Этапы 2-4 и 6 не зависят друг от друга и могут идти параллельно после этапа 1; порядок этапов 6-9 владелец уточняет по рынкам (вопрос В-10).

Правило бюджета веса: порог равен весу лучшего эталона на том же наборе знаков, умноженному на 1,25, с округлением. Эталон и набор записываются в `STAGE.md` до рисования. Свой рисунок без контраста и без оси ширины должен быть не тяжелее эталона; запас 25 % - на программное построение контуров.

Примечания:

- 🟢 В `glyphsets` 1.1.0 наборы Google Fonts определены только для латиницы, кириллицы, греческого и арабицы. Для остальных письменностей набор этапа задаётся списком языков Hyperglot, образцовыми знаками из `googlefonts/lang` (поле `exemplar_chars`) и CLDR 🟡 и фиксируется файлом `sources/<script>/charset.txt`.
- Язык считается поддержанным, когда пройдены ворота раздела 6 для этого языка. Наличие знаков поддержкой не называется.

### 2.3. Архитектура семейства

- **Один файл на письменность, одно имя в CSS.** Арабица - отдельные файлы `SABModulSansArabic[wght].ttf` и веб-подмножества; в CSS они подключаются под именем `SAB Modul Sans` с `unicode-range`. Браузер качает только то подмножество, знаки которого есть на странице.
- **Существующие файлы латиницы и кириллицы не меняются побайтно**, кроме этапов, где правка объявлена (0 и 2). Ворота: хеши из `FONT-SHA256.json` для не объявленных к правке файлов совпадают.
- **Сводная сборка для настольных программ** (один файл со всеми принятыми письменностями, кроме иероглифов) - отдельный продукт поставки; собирается слиянием принятых файлов.
- **Курсив.** В арабице, еврейском письме, письменностях Азии курсива нет. В «курсивном» объявлении `@font-face` для этих диапазонов указывается тот же прямой файл: браузер не синтезирует наклон.
- **Mono и Code.** Для письменностей с соединением букв и для иероглифов моноширинный рисунок - отдельная задача. По умолчанию Mono получает только цифры письменности (табличные) и знаки валют; буквы закрывает пара. Свой моноширинный рисунок - вопрос В-5.

## 3. Правила гармонизации с латиницей и кириллицей

Правила общие для всех этапов. Числа - стартовые; точные значения письменности записываются в `sources/<script>/DESIGN.md` до рисования и проверяются скриптом по реальным кривым, а не по контрольным точкам.

### 3.1. Латиница и кириллица: что добавляет этап 0

- Общие: U+02BC (апостроф-буква: украинский, кечуа, гуарани, аймара, языки майя), U+02BB (окина).
- Гуарани: `ẽ Ẽ ỹ Ỹ ĩ Ĩ ũ Ũ` и `g̃ G̃` (буква с комбинируемой тильдой U+0303: проверяется позиционирование, отдельного кода нет).
- Науатль и языки Мексики: сальтильо U+A78B, U+A78C 🟡; макроны уже есть.
- Языки майя, мапуче, кечуа, аймара: сочетания с U+02BC, `ü ñ` уже есть; проверка по `shaperglot check` для `qu_Latn ay_Latn gn_Latn yua_Latn quc_Latn arn_Latn nah_Latn` (коды языков сверить 🟡).
- Кириллица: `Җ җ Ҳ ҳ Ҷ ҷ Ӣ ӣ Ӯ ӯ` и остаток `GF_Cyrillic_Plus`.
- Функция `mkmk` и якоря для второго яруса знаков (нужны вьетнамскому, этап 2; закладываются сразу).

### 3.2. Вертикали

- Г-1. Линии строки (`hhea` и `OS/2 typo`) во всех файлах семейства одинаковы: Sans и Mono 1040 / -320 / 0. Новая письменность их не меняет. Ворота: значения совпадают.
- Г-2. `usWinAscent` и `usWinDescent` файла письменности могут вырасти, чтобы не обрезались верхние и нижние знаки; на высоту строки это не влияет.
- Г-3. Буква с одним знаком сверху и одним снизу укладывается в 1040 / -320. Двойные стопки (шадда с гласной, вьетнамские `Ấ Ễ`, тайский тон над верхней гласной, кхмерские подписные) могут выходить за линии строки, но не за `usWin*`; при `line-height` 1,4 в интерфейсе соседние строки не сталкиваются - проверяется снимком В10.
- Г-4. Для каждой письменности задаются свои опорные уровни и их отношение к латинским 500 и 700. Справка по эталонам 🟢: у семейства Noto латинские 536 и 714 при линиях 1069 / -293; у Noto Sans Arabic линии 1374 / -738, у IBM Plex Sans Arabic 1085 / -415; у Noto Sans Thai 1061 / -450; у Noto Sans Myanmar 1324 / -860. Если письменность не укладывается в 1040 / -320 без потери читаемости, это решается до рисования: либо уменьшением знаков письменности относительно латиницы (как делает Plex), либо общим пересмотром линий строки семейства - вопрос В-12.
- Г-5. Арабица: высота алифа - между высотой прописных и верхом выносных (стартовое 700-740 🟡), зубцы и петли - относительно 500, хвосты - не ниже -300. Греческое, армянское письмо: строчные 500, прописные 700. Тайская и лаосская: высота согласной 500-560 🟡, верхние гласные и тоны - в зоне 560-1040. Иероглифы: кегельная площадка 1000 на 1000, центр площадки согласован с серединой между базовой линией и высотой прописных.

### 3.3. Насыщенность по оси

- Г-6. Ось одна - `wght`, диапазон и именованные веса совпадают с латиницей: 200-900 у Sans и Mono. Мастера письменности совместимы для интерполяции.
- Г-7. Толщина основного штриха письменности на каждом весе равна латинской (56, 70, 80, 97, 115, 134, 161) с оптической поправкой не больше ±8 % 🟡; для плотных знаков (иероглифы, кхмерская, деванагари в жирных весах) поправка может быть больше и записывается по весам.
- Г-8. Серый тон абзаца. Замер: абзац языка этапа и абзац на английском и русском набраны одним кеглем (14, 16, 24 px), считается доля закрашенных пикселей в строке. Отношение к латинице - в пределах 0,90-1,10 🟡 на весах 400 и 700. Тот же замер делается для эталона этапа: своё отклонение не хуже, чем у эталона рядом со своей латиницей.
- Г-9. Характер рисунка сохраняется: штрих без контраста, те же скругления и срезы концов, что в латинице. Для арабицы это упрощённый насх с геометрическим характером, не куфи и не насталик; для тайской - рисунок без петель или с малыми петлями (решается пробой и ревью, риск Р-5).

### 3.4. Ширины

- Г-10. Средняя ширина знака и просветы подбираются по абзацу; проба - двуязычная строка интерфейса (подпись поля и значение).
- Г-11. В письменностях с соединением (арабица) стык соседних форм - на одной высоте и одной толщины: замер для всех пар форм, ступенька 0 единиц, перекрытие не больше 1 единицы.

### 3.5. Цифры

- Г-12. Европейские цифры 0-9 общие для всех письменностей и берутся из файла латиницы (в `unicode-range` письменности не входят).
- Г-13. Цифры письменности (арабско-индийские U+0660-0669, расширенные U+06F0-06F9, тайские U+0E50-0E59, лаосские, кхмерские, бирманские, деванагари U+0966-096F) по умолчанию табличные и имеют ширину латинской цифры: 630 в Sans, 620 в Mono, 600 в Code. Ворота: ширины равны на всей оси.
- Г-14. Высота цифр письменности согласована с латинскими (700) с оптической поправкой; базовая линия общая.
- Г-15. Формы цифр 4, 5, 6, 7 в U+06F0-06F9 зависят от языка: персидские, урду и синдхи различаются 🟡. Решается функцией `locl`; проверка - тест шейпинга с `lang=fa`, `lang=ur`, `lang=ps`.
- Г-16. Разделители: арабский десятичный U+066B, разделитель тысяч U+066C, процент U+066A - согласованы с цифрами.
- Г-17. Функции `tnum` и `pnum` действуют на цифры письменности так же, как на латинские.

### 3.6. Знаки валют

- Г-18. Этап 0 расширяет общий набор (сейчас 8 знаков) валютами обязательных регионов: Латинская Америка - `₲ ₡ ₱` (остальные пишутся буквами и `$`); Юго-Восточная Азия - `₫ ฿ ₭ ៛ ₱`; Китай, Япония, Корея - `¥` есть, `₩`, полноширинные `￥ ＄` идут в файл иероглифов; прочие - `₼ ₾ ֏ ₪ ₺ ₴ ₹ ₨ ₮ ₦ ₵ ₿` и сом U+20C0 🟡. Знаки, появившиеся в Unicode недавно (саудовский риял, дирхам ОАЭ) 🟡, - после сверки кодов.
- Г-19. Валюты письменности идут в её файл: афгани `؋` (U+060B), риал `﷼` (U+FDFC), риель `៛` (U+17DB), бат `฿` (U+0E3F) - дублируются в общем наборе символов.
- Г-20. Каждый знак валюты имеет табличный вариант шириной в цифру и стоит на одной линии с цифрами. Ворота: ширина в `tnum` равна ширине цифры.

### 3.7. Табличные цифры для Mono

- Г-21. В Mono каждая цифра любой письменности, знак валюты, разделитель и пробел имеют ширину 620 на всей оси. Ворота: `test_mono_width.py` расширяется на новые знаки; столбец сумм из латинских и арабско-индийских цифр совпадает по правому краю с точностью 0 единиц.
- Г-22. Комбинируемые знаки в Mono имеют нулевую ширину. Иероглиф и полноширинный знак в Mono занимают ровно две ячейки (1240) - если иероглифы подключены парой, это проверяется на паре и подгоняется `size-adjust`.

## 4. Этап 1 в деталях: арабица

### 4.1. Языки и что каждый требует

| Язык | Код | Особенности |
|---|---|---|
| Арабский | `ar` | 28 букв, хамза на носителях, та-марбута, алиф-максура, огласовки, лам-алиф |
| Персидский | `fa` | `پ چ ژ گ`, `ک` (U+06A9), `ی` (U+06CC), нулевой несоединитель U+200C обязателен, цифры U+06F0-06F9 |
| Дари | `prs` | набор персидского; примеры - афганские |
| Пушту | `ps` | `ټ ځ څ ډ ړ ږ ښ ګ ڼ ې ۍ` плюс `ی ي ئ`; пять разных «йа» различаются точками и хвостом - главная зона ошибок |
| Урду | `ur` | `ٹ ڈ ڑ ں ہ ھ ے ۓ`, точка U+06D4; традиционный стиль - насталик (риск Р-4) |

🟢 Обязательные знаки пушту, персидского и урду сверены с определениями Shaperglot 1.2.2 (`shaperglot describe ps_Arab`, `fa_Arab`, `ur_Arab`) и с полем `exemplar_chars` файлов `ps_Arab`, `fa_Arab`, `prs_Arab`, `ur_Arab`, `ar_Arab` из `googlefonts/lang`.

### 4.2. Набор знаков

- Основа: `GF_Arabic_Core` (224 знака) - `glyphsets print-unicodes GF_Arabic_Core`.
- Добавка: все обязательные и вспомогательные знаки `ps_Arab`, `ur_Arab`, `fa_Arab`, `ar_Arab` из Shaperglot, Hyperglot и `exemplar_chars` (включая пунктуацию пушту `۽ ۾` и знак промилле `؉`), которых нет в основе.
- Управляющие: U+200C, U+200D, U+200E, U+200F, U+061C, U+2066-2069 (пустые глифы нулевой ширины). Их отсутствие - причина, по которой IBM Plex Sans Arabic не проходит проверку пушту (раздел 1.4).
- Пунктуация: `، ؛ ؟ ٪ ٫ ٬ ۔`, татвиль U+0640, кавычки и скобки с зеркальными парами.
- Цифры: U+0660-0669, U+06F0-06F9. Валюты: `؋`, `﷼`.
- Формы совместимости U+FB50-FDFF, U+FE70-FEFC: кодируются только те, что требует `GF_Arabic_Core`; остальные формы живут без кодов, как позиционные варианты.
- Файл `sources/arabic/charset.txt` фиксируется до рисования; изменение - новой версией с причиной.

### 4.3. Исходники и сборка

- Источник рисунка остаётся программным, как в латинице: скелеты в единицах кегля, расширение штриха, объединение контуров. Агенты надёжнее правят числа в коде, чем кривые в графическом редакторе.
- Каталог `sources/arabic/`: `skeletons.py` (базовые формы без точек), `dots.py` (точки и знаки как компоненты с якорями), `joining.py` (четыре формы на букву: isol, init, medi, fina), `features.fea`, `anchors.json`, `charset.txt`, `DESIGN.md`.
- Буква собирается из основы и точек: одна основа обслуживает группу букв (`ب ت ث پ ټ`). Правка основы меняет всю группу согласованно; компоненты уменьшают вес файла. Справка 🟢: в подмножестве `GF_Arabic_Core` у Noto Sans Arabic 330 глифов на 224 знака, у Vazirmatn 551, у IBM Plex Sans Arabic 746.
- Промежуточный формат обмена - UFO и designspace; компиляция - fontmake (ufo2ft) с закреплёнными версиями 🟡. Так функции `mark`, `mkmk`, `kern` строятся штатными генераторами из якорей. Решение о формате - вопрос В-6.
- Одна команда: `python tools/build_script.py arabic --clean` собирает мастера, статические TTF и OTF, вариативный файл, WOFF2 и подмножества в пустой каталог.
- Зависимости закреплены с хешами (`requirements-build.txt`), время сборки берётся из `SOURCE_DATE_EPOCH`.

### 4.4. Функции OpenType

Письменность `arab`; языковые системы `dflt`, `ARA `, `FAR `, `PAS `, `URD `, `SND `, `KUR ` 🟡 (теги сверить с реестром OpenType).

| Функция | Что делает | Проверка |
|---|---|---|
| `ccmp` | разложение и сборка составных знаков; NFC и NFD дают один рисунок | пары строк NFC/NFD: равные глифы и позиции |
| `locl` | формы по языку: цифры 4-7 для `fa`, `ur`, `sd`; `ی` и `ے` в пушту и урду; `ه` в урду и курдском | тест с `lang=` на каждую замену |
| `isol init medi fina` | формы соединения | независимый оракул: ожидаемая форма каждого знака вычисляется по `ArabicShaping.txt` из Unicode и сравнивается с глифом из HarfBuzz, на всех словах словаря |
| `rlig` | обязательный лам-алиф (`لا لأ لإ لآ`, изолированная и конечная формы) | 8 последовательностей, один глиф лигатуры; огласовка между буквами стоит на своей части |
| `calt` | контекстные поправки стыков (высокие зубцы в цепочке `ببب`, `سـ` перед `ـي`) | снимки цепочек; столкновений 0 |
| `liga` | необязательные лигатуры | в этапе 1 не делаются: мешают поиску и выделению |
| `mark` | огласовки на букве: якоря верх и низ на каждой форме | каждая пара «основа-знак» даёт ненулевое позиционирование; столкновений с точками 0 |
| `mkmk` | знак на знаке: шадда с фатхой, даммой, касрой, танвином; хамза с огласовкой | все двойные сочетания; второй знак выше первого, без пересечений |
| `kern` | пары несоединяемых букв (`ر و د ا` перед следующей), пары с пунктуацией и цифрами | список пар в `kerning.json`; столкновений 0 |
| `curs` | курсивное примыкание | не используется: базовая линия ровная; запись в `DESIGN.md` |
| `tnum pnum` | цифры письменности | Г-13, Г-17 |
| Кашида | глиф татвиля U+0640 той же толщины и высоты, что соединительный штрих; цепочка `ـــ` без ступенек; удлинение слов выполняет программа вёрстки, не шрифт 🟡 | слово с 1, 3, 10 татвилями в каждой позиции; разрыв 0 единиц |

Таблица `GDEF` обязательна: классы основ, знаков, лигатур; якоря частей лигатуры лам-алиф.

### 4.5. Тестовые строки

Каталог `tests/shaping/arabic/`:

- `forms.json` - все буквы набора во всех допустимых позициях, сгенерированы по `ArabicShaping.txt`;
- `lam-alef.json`, `marks.json`, `mkmk.json`, `kashida.json`, `digits-locl.json`, `zwnj-zwj.json`;
- `samples-<lang>.json` - поля `sample_text` (`masthead_full`, `styles`, `tester`, `poster_*`, `specimen_*`) из файлов `ar_Arab`, `fa_Arab`, `prs_Arab`, `ps_Arab`, `ur_Arab` репозитория `googlefonts/lang`; те же строки идут на снимки В10 и на пробы для ревью;
- `bidi.json` - смешанные строки: арабский текст с латинским словом, суммой, датой, номером счёта, скобками;
- `words-<lang>.txt` - по 5 000 частотных слов на язык из источника с открытой лицензией 🟡 (источник и лицензия - в `tests/shaping/SOURCES.md`);
- `ui-<lang>.txt` - реальные строки интерфейса FCB на языке этапа: подписи полей, кнопки, сообщения об ошибках, суммы с валютой.

Ожидаемый вывод HarfBuzz хранится в репозитории. Первичное ожидание по числу и порядку кластеров сверяется с выводом эталонов на тех же строках (Noto Sans Arabic, Vazirmatn): расхождение в числе глифов на слово разбирается по каждому случаю. Изменение ожиданий - отдельная правка с причиной, её принимает приёмщик.

### 5.1. Латинская Америка (этап 0)

- Языки: испанский, португальский (уже проходят 🟢); гуарани, кечуа, аймара, науатль, юкатекский майя, киче, мапуче.

- Особенности: `¿ ¡` и их вариант для прописных (`case`), `ª º`, кернинг пар с `ñ`, `ç`, `ã õ`; буква с отдельной тильдой `g̃` - только через `mark`.

### 5.2. Юго-Восточная Азия, латиница (этапы 0 и 2)

- Индонезийский, малайский, филиппинский: обязательные знаки есть 🟢; ворота - `shaperglot check id_Latn ms_Latn fil_Latn`, строки `id_Latn`, `fil_Latn` на снимках. Валюты `₱`, `Rp`, `RM` (буквами).
- Вьетнамский (этап 2): `GF_Latin_Vietnamese` (231 знак), 134 буквы с одним и двумя знаками 🟡, рог `ơ ư`, крюк `◌̉`, точка снизу `◌̣`, донг `₫`.
- Особенности: второй знак ставится сверху-справа от циркумфлекса, а не строго над ним (вьетнамская традиция); прописные со стопкой (`Ấ Ễ Ổ`) выше 1040 - решение по Г-3; NFC и NFD дают один рисунок (`ccmp`, `mark`, `mkmk`).
- Проверки сверх общих: `shaperglot check vi_Latn` полностью; `glyphsets coverage` - 100 % `GF_Latin_Vietnamese`; все 134 буквы в NFC и NFD - попиксельно равны; высота стопки сравнивается с `inter` и `notosans` на одном кегле; снимок трёх строк подряд с `line-height` 1,2 и 1,4 - столкновений 0.
- Вес: отдельное подмножество `vietnamese` не больше 35 КБ 🟡 (качается только при вьетнамском тексте).

### 5.3. Тайская и лаосская письменности (этап 3)

- Языки: тайский, лаосский. Наборы: U+0E01-0E5B (87 знаков), U+0E80-0EFF; цифры письменности; `฿ ₭`.
- Шейпинг: слогового движка нет, но четыре яруса - согласная, нижняя гласная, верхняя гласная, тон над ней. Функции: `ccmp` (разложение сара-ам U+0E33, U+0EB3), `mark`, `mkmk`, контекстные замены: сдвиг верхних знаков влево над согласными с высоким хвостом (`ป ฝ ฟ`), опускание тона при отсутствии верхней гласной, снятие нижней части у `ญ ฐ` перед нижней гласной.
- Пробелов между словами нет: перенос строки делает браузер по словарю 🟡; шрифт на это не влияет, проверяется в В11 как свойство интерфейса.
- Рисунок: традиционный с петлями или современный без петель. Эталоны обоих видов: `notosansthai` (с петлями), `ibmplexsansthai` (без петель, геометрия). Выбор - по пробе и ревью носителя (вопрос В-13).

- Вес: тайская не больше 32 КБ, лаосская не больше 27 КБ.

### 5.4. Кхмерская и бирманская письменности (этап 4)

- Языки: кхмерский, бирманский. Наборы: U+1780-17FF, U+19E0-19FF; U+1000-109F; `៛`, `K` (буквой).
- Шейпинг кхмерский: подписные согласные через знак коенг U+17D2 (`pref`, `blwf`, `abvf`, `pstf`, `pres`, `blws`, `abvs`, `psts` 🟡), гласные вокруг согласной с перестановкой, стопки до трёх уровней вниз. Справка 🟢: у Noto Sans Khmer 334 глифа на 146 знаков, линии `usWin` 1155 / 707.

Справка 🟢: 474 глифа на 160 знаков, линии 1324 / -860, подмножество 121 КБ - самая тяжёлая письменность региона. Старые устройства с кодировкой Zawgyi шрифтом не решаются 🟡 - запись в ограничениях.

- Проверки сверх общих: полный список сочетаний «согласная + коенг + согласная» и медиалей - 0 пунктирных кругов, 0 столкновений; сравнение кластеров с эталоном; строки `km_Khmr`, `my_Mymr`.

### 6.1. Ревью носителем языка

ИИ-агент не носитель: он не видит, что буква «выглядит как чужая». Автоматика ловит ошибки соединения и столкновения, но не привычность рисунка. Поэтому:

- **Кто.** На каждую письменность - один шрифтовой консультант, работающий с ней профессионально. На каждый язык этапа - не меньше трёх читателей-носителей, не занятых в проекте.
- **Как.** Консультант получает PDF-пробы (алфавит во всех формах, слова, абзацы на 9, 12, 16, 24 pt, все веса, пары с латиницей, тот же текст эталоном) и опросный лист: замечания по буквам с важностью «блокирует / исправить / пожелание». Читатели проходят тест: чтение вслух абзаца с подсчётом запинок, опознание похожих букв (для пушту - пять «йа», `ځ څ`, `ړ ږ`, `ښ`; для тайской - `ค ด ต`, `ผ ฝ พ ฟ`; для китайского - знаки, различные в упрощённой и традиционной форме), сравнение вслепую с эталоном по удобству чтения.
- **Порог.** 0 замечаний «блокирует»; все «исправить» закрыты или отклонены с записанной причиной; доля верно опознанных букв не ниже, чем у эталона минус 2 процентных пункта 🟡.
- **Свидетельство.** `checks/stages/<..>/native-review/`: пробы, заполненные листы, ответы; личные данные читателей в публичный репозиторий не кладутся - только роль и язык.
- **Если носителя нет.** Этап получает статус `ACCEPTED-TECH` (технические ворота пройдены, ревью нет). В этом статусе язык не объявляется поддержанным, файл поставляется как предварительный, в интерфейсе для языка по умолчанию остаётся парный шрифт. Статус `ACCEPTED` без В17 не ставится.
- **Заменители, которые ревью не отменяют, но снижают риск до него:**
  - сверка строения с эталонами: число и место точек и знаков, высота стыков, пропорции основы, отношение высот к латинице - замером по двум-трём эталонам; выход за разброс эталонов больше чем на 15 % 🟡 требует записанной причины;
  - машинное чтение: слова словаря, набранные шрифтом этапа, распознаёт открытая программа распознавания текста; доля верных слов не ниже, чем у эталона минус 2 процентных пункта 🟡;
  - слепое ревью вторым агентом-дизайнером по тем же пробам без вывода первого.

## 7. Роли и порядок работы этапа

### 7.1. Роли

| Роль | Модель | Делает | Не делает |
|---|---|---|---|
| Ведущий | - | открывает этап, фиксирует пороги, раздаёт задания, коммитит, сообщает владельцу | не рисует и не принимает раздачу без замера приёмщика |
| Дизайнер | Opus | `DESIGN.md`, скелеты, формы соединения, якоря, логика функций, разбор замечаний ревью | не меняет пороги и ожидаемые строки тестов |
| Механик | Sonnet | сборка, подмножества, раннер ворот, тестовые строки, замер эталонов, снимки, отчёты | не правит рисунок и не объявляет приёмку |
| Второй дизайнер (слепое ревью) | Opus, свежая сессия | оценивает пробы без вывода первого дизайнера | не видит отчётов исполнителей |
| Приёмщик | Fable | на чистой копии сам запускает `tools/gate.py`, сверяет хеши, читает сырые отчёты, проверяет мутанты | не правит файлы шрифта; не получает вывода исполнителей заранее |
| Носитель и консультант | человек | В17 | - |

### 7.2. Порядок этапа

1. **Открытие.** Ведущий создаёт `checks/stages/<NN-script>/STAGE.md`: языки, `charset.txt`, эталоны, пороги В1-В18, бюджеты веса, список исключений Font Bakery. С этого момента пороги заморожены.
2. **Замер эталонов.** Механик скачивает эталоны и образцы текста по манифесту с суммами SHA-256 (`tools/fetch_refs.py`, каталог `refs/` вне git), снимает с них метрики, вес подмножества, результаты Shaperglot и вывод HarfBuzz на тестовых строках - `refs-baseline.json`.
3. **Тесты до рисунка.** Механик готовит тестовые строки, оракул форм, страницу проверки интерфейса, мутанты. Приёмщик проверяет, что ворота красные на пустом шрифте и на мутантах и зелёные на эталоне там, где эталон обязан проходить (В5-В8).
4. **Проба.** Дизайнер рисует 12-15 ключевых знаков в весах 200, 400, 900 и слова из них (для арабицы: `ا ب ح د ر س ص ط ع ف ل م ن ه و ی`). Проба рядом с латиницей SAB Modul и с эталоном уходит на слепое ревью и, если есть, консультанту. Без одобренной пробы полный набор не рисуется.
5. **Полный набор, Regular.** Все знаки, формы, якоря, функции - в одном весе. Ворота В6-В8 на Regular.
6. **Веса и ось.** Мастера 200 и 900, интерполяция, ворота В9.
7. **Сборка и веб.** Все форматы, подмножества, CSS, ворота В1-В4, В10-В16.
8. **Ревью носителем.** В17. Замечания - дизайнеру, правка, повтор затронутых ворот.
9. **Приёмка.** Приёмщик на чистой копии от коммита этапа выполняет полный прогон, пишет `GATE.json` и `VERDICT.md`. Ведущий сам перепроверяет три ворот на выбор.
10. **Выпуск.** Версия, `CHANGELOG.md`, `FONT-SHA256.json`, `checks/SUMMARY.json`, `ACCEPTANCE.md` (новые ограничения названы прямо), `README.md`, блок CSS в поставке.

Итерация короткая: одна правка - пересборка - сравнение с прошлой версией на той же пробе. Ухудшение откатывается.

```text
  shaping/            вывод HarfBuzz, расхождения с ожиданием
  screens/            снимки по движкам и кеглям, листы сравнения с эталоном, карта расхождений
  weight.json         размеры WOFF2, бюджет, вес эталона на том же наборе
  mutants/            отчёты ворот на испорченных образцах
  native-review/      пробы, опросные листы, ответы
  exceptions.md       каждое принятое исключение: проверка, причина, кто принял
  VERDICT.md          вердикт приёмщика: ACCEPTED / ACCEPTED-TECH / REJECTED
```

Статусы различаются, как сейчас: PASS, FAIL, WARN, ERROR, SKIP, «не проводилось». Пропуск объясняется.

### 7.4. Как не допустить «принято по отчёту»

- С-1. Вердикт пишется только из `GATE.json`, а `GATE.json` пишет только скрипт. Рукой статус не ставится.
- С-2. Отчёты относятся к файлам по хешу. Хеш в `hashes.json` не совпал с файлом в поставке - отчёт недействителен.
- С-3. Приёмщик работает в чистой копии от коммита, сам ставит окружение по закреплённым версиям и сам собирает шрифт. Готовые файлы исполнителя он сравнивает со своими по хешу (это и есть В14).
- С-4. Текст исполнителя «всё прошло» доказательством не считается. Задание исполнителю заканчивается командой и её выводом.
- С-5. Приёмщик не получает выводов исполнителей до своего прогона; слепой ревьюер не получает вывода дизайнера.
- С-6. Пороги и ожидаемые строки тестов правит только ведущий отдельным коммитом с причиной. Изменение порога после начала рисунка - событие, о котором сообщается владельцу.
- С-7. Мутанты (В18) доказывают, что ворота способны покраснеть; прогон на эталоне доказывает, что они способны позеленеть.
- С-8. FAIL не переименовывается. Исключение - отдельная запись в `exceptions.md`, сырой статус остаётся в отчёте.
- С-9. Старое свидетельство не переносится на новые файлы: после любой правки шрифта затронутые ворота перезапускаются, перед выпуском - все.

## 8. Лицензия

- 🟢 SAB Modul выпущен под SIL OFL 1.1 с Reserved Font Name «SAB Modul» (`OFL.txt`, `LICENSE`, записи в каждом файле).
- Расширение выпускает сам правообладатель, поэтому новые файлы могут носить имя SAB Modul. Сторонняя доработка под этим именем по-прежнему требует письменного разрешения.
- **Свои контуры - основной путь.** `METHODOLOGY.md` заявляет оригинальные контуры из собственной геометрии. План это сохраняет: эталоны используются для измерений, сравнения и как парный шрифт; их контуры не извлекаются и не правятся. Ворота В16 проверяют это замером.
- **Эталоны в репозиторий не кладутся.** Они скачиваются по манифесту в каталог вне git; в репозитории - только манифест (адрес, версия, SHA-256, лицензия) и результаты замеров.
- **Можно ли опираться на другие OFL-шрифты.** Да, OFL 1.1 разрешает изменять и объединять шрифты при трёх условиях 🟡 (сверить с текстом лицензии и FAQ на openfontlicense.org):
  - результат распространяется только под OFL 1.1, целиком;
  - copyright исходного шрифта сохраняется и дополняется своим; в `OFL.txt` и в записи copyright файла стоят обе строки;
  - Reserved Font Name исходного шрифта в имени производного не используется. У шрифтов Noto RFN не объявлен 🟡; у других он бывает (например, у Source Han Sans - «Source» 🟡) - проверяется по `OFL.txt` каждого.
- **Как оформлять производную сборку** (нужна для гармонизированной пары иероглифов, раздел 9, и если владелец разрешит заимствование для дальних письменностей, вопрос В-4): каталог `sources/<script>/upstream/` с исходным `OFL.txt`, версией, адресом и хешем; строка в `THIRD-PARTY-NOTICES.md`; запись в `FONTLOG` 🟡 о том, что изменено; пометка в `README.md`, что письменность производна от такого-то шрифта; отдельное имя семейства, по которому видно, что рисунок не оригинальный (вопрос В-3).
- **Что берётся без вопроса** (не контуры): данные Unicode (лицензия Unicode), определения языков Hyperglot и Shaperglot, наборы Google Fonts, образцы текста `googlefonts/lang` (Apache-2.0) - с записью источника и лицензии в `THIRD-PARTY-NOTICES.md`.
- **Парные шрифты в интерфейсе** распространяются как есть или подмножеством, под своим именем, со своим `OFL.txt` рядом. Подмножество - это изменение шрифта; при объявленном RFN у парного шрифта подмножество под его именем требует проверки условий 🟡.
- **Каталог Google Fonts.** Наличие RFN и текущие исключения `googlefonts` означают, что вхождение в каталог не заявляется (`ACCEPTANCE.md`). План этого не меняет; вопрос В-8.

## 9. Китай и иероглифы: свой рисунок или гармонизированная пара

### 9.1. Что требуется

- Упрощённое письмо (материковый Китай): минимум - GB 2312, 6 763 иероглифа; современный перечень общеупотребительных знаков - 8 105 🟡.
- Традиционное письмо (Тайвань): Big5, около 13 тысяч иероглифов 🟡; частый уровень - 5,4 тысячи.
- Гонконг: традиционное письмо с местными формами знаков и добавочным набором HKSCS (кантонские знаки) 🟡; язык `yue`. Эталон - отдельная гонконгская сборка Noto 🟡 (в замер не входила).
- Один и тот же код в материковой, тайваньской, гонконгской, японской и корейской традициях рисуется по-разному: нужен либо отдельный файл на регион, либо функция `locl` по языку (`zh-Hans`, `zh-Hant`, `zh-HK`, `ja`, `ko`).
- Пунктуация и полноширинные знаки: положение в площадке различается по регионам (у угла или по центру).

## 10. Временная пара для интерфейса

Действует с первого дня и до приёмки своей письменности. Правила:

- П-1. Парные шрифты лежат на своём сервере рядом с SAB Modul; внешние сети доставки шрифтов не используются.
- П-2. В цепочке шрифтов SAB Modul стоит первым: латиница, кириллица, европейские цифры, общая пунктуация и валюты всегда берутся из него.
- П-3. Каждая письменность - отдельное объявление `@font-face` с `unicode-range`; браузер скачивает файл, только когда на странице есть знак диапазона. Пользователь русского интерфейса арабский шрифт не качает.
- П-4. `font-display: swap`. Предзагрузка (`preload`) - только для письменности языка интерфейса пользователя.
- П-5. Метрики пары подгоняются к SAB Modul дескрипторами `size-adjust`, `ascent-override`, `descent-override`, чтобы строка не прыгала; значения считаются из замеров раздела 1.4 (например, латинская высота строчных у Noto 536 против 500 у SAB Modul), поддержка дескрипторов в движках сверяется 🟡.
- П-6. Парный шрифт проходит ворота В5, В6, В8, В10, В11, В12 для языков, которые он закрывает: пара принимается замером, а не по названию.
- П-7. После приёмки своей письменности меняется один блок CSS; пара остаётся запасной в конце цепочки.
- П-8. Пара поставляется подмножеством с одной осью `wght` (ось ширины закрепляется): так Noto Sans Arabic на наборе ядра весит 65 КБ вместо 845 КБ полного TTF 🟢.

```css
/* свой шрифт - как сейчас в SAB-Modul-1.0/WEB/fonts.css */
@font-face {
  font-family: 'SAB Modul Sans';
  font-weight: 200 900;
  font-display: swap;
  src: url('./SABModulSans[wght]-latin.woff2') format('woff2');
  unicode-range: U+0020-007E, U+00A0-00FF; /* сокращено */
}

/* пара: арабица, до приёмки этапа 1 */
@font-face {
  font-family: 'FCB Pair Arabic';
  font-weight: 100 900;
  font-style: normal;
  font-display: swap;
  src: url('./pair/NotoSansArabic[wght]-arabic.woff2') format('woff2');
  unicode-range: U+0600-06FF, U+0750-077F, U+0870-088E, U+0890-0891, U+0897-08E1,
                 U+08E3-08FF, U+200C-200F, U+FB50-FDFF, U+FE70-FE74, U+FE76-FEFC;
  size-adjust: 100%;        /* подбирается замером, П-5 */
}
/* то же объявление с font-style: italic и тем же файлом - чтобы браузер не наклонял арабицу */

/* пара: тайская */
@font-face {
  font-family: 'FCB Pair Thai';
  font-weight: 100 900;
  font-display: swap;
  src: url('./pair/NotoSansThai[wght]-thai.woff2') format('woff2');
  unicode-range: U+0E01-0E5B, U+200C-200D, U+25CC;
}

:root {
  font-family: 'SAB Modul Sans', 'FCB Pair Arabic', 'FCB Pair Thai', system-ui, sans-serif;
}
:root:lang(zh) {
  /* при слабой сети иероглифы - системным шрифтом, 0 байт */
  font-family: 'SAB Modul Sans', system-ui, 'FCB Pair SC', sans-serif;
}
```

После приёмки этапа 1 блок пары заменяется на `font-family: 'SAB Modul Sans'` с файлом `SABModulSansArabic[wght]-arabic.woff2` и тем же `unicode-range`.

Требования к самому интерфейсу (проверяются воротами В11 на стороне продукта): `dir` и `lang` на корневом элементе, логические свойства CSS (`margin-inline-start` вместо `margin-left`), зеркальные значки направления, изоляция сумм, дат и номеров счетов (`<bdi>` или `unicode-bidi: isolate`), выбор цифр по настройке локали, а не шрифтом, `line-height` не меньше 1,4 для письменностей со стопками знаков.

## 14. Вопросы владельцу

Ведущий по этим вопросам не решает. К каждому - варианты и рекомендация.

- **В-1. Что считать готовым «глобальным шрифтом».**
  - а) свои рисунки обязательных регионов (арабица, латиница и кириллица, Юго-Восточная Азия), иероглифы - гармонизированная пара, остальное - пара по спросу; б) свои рисунки всего, кроме иероглифов; в) свои рисунки всего.
  - Рекомендация: а) как цель первого года.
- **В-2. Ревью носителем.** а) платный шрифтовой консультант на письменность и по три читателя на язык; б) только читатели из своего круга; в) без носителя, статус `ACCEPTED-TECH` и пара по умолчанию.
  - Рекомендация: а) для арабицы, тайской, кхмерской, бирманской, деванагари; б) для вьетнамского, греческого, армянского, грузинского, иврита.
- **В-3. Китай и иероглифы** (раздел 9). а) пара без изменений и системный шрифт; б) гармонизированная пара на OFL-основе под отдельным именем семейства; в) свои кана и хангыль плюс б); г) свои иероглифы.
  - Рекомендация: а) сразу, б) как целевая редакция. Для б) нужно решение об имени: производная сборка не подходит под заявление об оригинальных контурах.
- **В-4. Заимствование контуров из открытых шрифтов для дальних письменностей** (кроме иероглифов). а) никогда; б) разрешить для этапов 9+ с оформлением по разделу 8.
  - Рекомендация: а).
- **В-5. Mono и Code для арабицы и письменностей Азии.** а) только цифры и валюты, буквы - пара; б) свой моноширинный рисунок отдельным этапом.
  - Рекомендация: а).
- **В-6. Формат исходников новых письменностей.** а) программные скелеты, как сейчас, плюс UFO как формат обмена и fontmake для компиляции; б) только программные скелеты и своя сборка функций; в) рисунок в шрифтовом редакторе.
  - Рекомендация: а).
- **В-7. Урду.** а) общий рисунок арабицы SAB Modul (насх); б) для урду постоянная пара с насталиком; в) свой насталик отдельным этапом.
  - Рекомендация: а) для интерфейса, решение по б) - после ревью читателями урду.
- **В-8. Каталог Google Fonts.** а) не заявляем, RFN сохраняем; б) готовим отдельную редакцию под требования каталога.
  - Рекомендация: а).
- **В-9. Имена файлов и семейств.** а) отдельные файлы по письменностям под общим именем в CSS и сводный файл для настольных программ; б) один большой файл на семейство.
  - Рекомендация: а) - из-за веса при слабой сети.
- **В-10. Порядок рынков после обязательных регионов.** Предложен: Кавказ и Средиземноморье, Индия, Япония и Корея. Нужен порядок по банковским рынкам от владельца.
- **В-11. Бюджет веса.** Предложено правило «эталон × 1,25» и числа таблицы 2.2. Нужны ли более жёсткие числа под конкретные сети (например, первый экран целиком не больше 100 КБ шрифтов).
- **В-12. Линии строки семейства.** Арабица, вьетнамские стопки, бирманская не помещаются в 1040 / -320 так свободно, как у эталонов. а) линии не трогаем, письменности рисуются компактнее, интерфейс держит `line-height` не меньше 1,4; б) линии строки семейства пересматриваются один раз для всех файлов (меняет вёрстку существующих документов).
  - Рекомендация: а).
- **В-13. Тайский рисунок.** а) без петель, в характере SAB Modul (эталон IBM Plex Sans Thai); б) с петлями (эталон Noto Sans Thai).
  - Рекомендация: решать после пробы и ревью носителя; стартовая проба - а) с вариантом б) рядом.
- **В-14. Облегчение существующей латиницы и кириллицы (Ф-11).** Это правка принятых файлов. а) делать в этапе 0; б) не трогать принятые файлы.
  - Рекомендация: а) - экономия около 70 КБ на первом экране.
